## Разовая настройка

```bash
python setup.py --sheets                      завести листы и заголовки
python setup.py --plan ../data/план_партии_1.tsv   залить партию в лист ПЛАН
python setup.py --form ../data/план_партии_1.tsv   список для выпадающего списка формы
```

🔴 **Плана партии в этом репозитории нет и быть не должно** - он публичный, а план
это содержание работы. Файл лежит в приватном `Контент_Завод_v2` и передается путем.
Скрипт возит данные, но не хранит их.

Все три команды безопасно повторять: существующие листы не трогаются, заголовки
не перезаписываются, строки плана не дублируются.

## Куда это переезжает

**Содержимое `pipeline/` становится корнем ПУБЛИЧНОГО репозитория `foxlik-pipeline`.**
(Строка выше говорила «приватного» - это была описка, замеченная 27.08. Публичный он
не по недосмотру, а по расчету минут: у публичных репозиториев время работы Actions
не считается вовсе → [АРХИТЕКТУРА §5](../управление/АРХИТЕКТУРА_СЕРВИСА.md).)
Не подпапкой: расписание и проверки рассчитывают, что `lib/`, `tick.py` и `tests/`
лежат в корне. Аналитика и доступы туда не едут - там только код.

## Зависимости

**Их нет намеренно.** Только стандартная библиотека Python - код должен запускаться
и в локальном venv без `pip install`, и в GitHub Actions без шага установки.

Дороже всего это обошлось на входе в Google: сервисный аккаунт подписывает JWT
алгоритмом **RS256**, а RSA в стандартной библиотеке нет (замер 27.08: в venv нет
ни `cryptography`, ни `rsa`, ни `jwt`, ни `google-auth`). Написали сами - вся
математика сводится к `pow(m, d, n)`, встроенному в Python. **Сверено с openssl 3.5.5:
подпись совпала побайтно**, проверка живет в `lib/google_auth.py` и падает при расхождении.

## 🔴 Что API отдает, а что нет (справочник Meta прочитан 27.08)

| Нужно нам | Через API | Как берем |
|---|---|---|
| Репосты - **наш гейт** | ✅ `shares` через `/insights` | автоматически |
| Просмотры, охват, сохранения | ✅ `views`, `reach`, `saved` | автоматически |
| **Подписки с конкретного ролика** | ❌ **такой метрики нет** | только ручной экспорт CSV |
| Пропуск первых 3 секунд | ✅ `reels_skip_rate` | собираем, решений не принимаем |

⚠️ **Ловушка, которая стоила бы дня.** Поля `shares_count` и `saved_count` у самого медиа
справочник помечает «Available for Instagram API with **Facebook Login** only», а мы сидим
на Instagram Login. Но метрика `shares` на endpoint `/insights` такой пометки не имеет.
**Поэтому все берется через `/insights`, а не через поля медиа.**

**Следствие для петли:** гейт автоматизируется целиком, метрика победы - нет.
Ручной экспорт CSV из Business Suite остается навсегда, и это устройство, а не недоделка.

## Живые прогоны

Selftest доказывает **логику**, `live_check.py` - **работу**.

```bash
python live_check.py doctor           что готово, чего не хватает
python live_check.py telegram-send    карточка приемки владельцу
python live_check.py telegram-peek    посмотреть очередь, ничего не трогая
python live_check.py telegram-read    забрать нажатие, снять кнопки, подтвердить
```

## 🔴 Что дали живые прогоны (27.08)

Четыре находки, которых проверки на подставном HTTP сделать не могли **в принципе**.
Каждая правила код.

**1. Токен бота утек в текст ошибки.** Telegram кладет токен прямо в адрес запроса,
и неотловленная ошибка напечатала его целиком в трассировку. В GitHub Actions такая
трассировка уходит в лог. Лечение - `http.mask()` на всех выходах, включая журнал такта.

**2. `answerCallbackQuery` вызывать нельзя.** Дословный ответ Telegram:
`query is too old and response timeout expired`. Идентификатор нажатия живет секунды,
а такт у нас 30 минут - постоянного процесса нет. Хуже того: **после его неудачи
нажатие пропало из очереди**, хотя больше его ничто не трогало. Метод удален.
Обратная связь владельцу идет правкой самого сообщения (`lock`) - она работает
при любой задержке.

**3. Чтение очереди ее не разрушает.** Проверено прямо: 13 обновлений прочитаны,
показаны снова, снова и снова. Значит порядок «чтение → работа → подтверждение»
надежен, и упавший такт не съедает нажатие.

**4. Подряд идущие опросы недоговаривают.** Первый вызов отдал 13 обновлений, три
следующих подряд - по одному, через паузу опять все 13. Ничего не пропало, но
**пустой ответ на быстрый повторный опрос не доказывает, что очередь пуста**. Такту
в полчаса это не мешает, отладке мешает сильно: два раза принял это за «не нажали».

**5. Секрет в журнале такта проверка пропустила.** Таблицу и сообщение владельцу
почистили по месту, а `print` в журнале забыли - увидели глазами в выводе. Отсюда
правило: чистка стоит **в одной точке вывода**, а не по местам.

## 🔴 Что дал сквозной прогон формы (27.08)

**1. Папка загрузок формы - отдельный объект с отдельными правами.** Таблица роботу
открыта, папка - нет: `File not found` на файл, который в браузере открывается. Первый
настоящий ролик уперся бы в это 4 сентября. Лечится расшариванием папки на почту робота
(права Читатель). **Проверка добавлена в `doctor`** - строка «Папка сдач», и она умеет
падать: подменили идентификатор на несуществующий, проверка сказала HTTP 404.

**2. Имя колонки почты угадать нельзя.** Google называет ее «Адрес электронной почты»,
код ждал «Электронная почта». `row.get` вернул бы пустоту, «Креатор» в ПУБЛИКАЦИЯХ
остался бы пустым, и главный срез петли молча исчез бы. В `tests/test_tick.py` теперь
лежит **дословный список колонок, снятый с живой формы**, и проверка падает при расхождении.

**3. Снимок доступности страницы соврал.** Дерево показало пустой редактор без единого
вопроса, хотя на скриншоте все на месте: элементы дорисовываются лениво. Тот же класс,
что и «пустой ответ Telegram не значит пустую очередь»: **отсутствие в выводе инструмента
не есть отсутствие в реальности**.

## Чего проверки не докажут

Ни одной живой публикации не сделано - нет токенов Instagram и ВК. Это этап 0 сборки,
и до него вся ветка публикации остается непроверенной.
